# Engineering log

Decisions, assumptions, test results, defects and lessons learned while building the ArcVault triage workflow.
The evaluator-facing summary is in [README.md](README.md); this file keeps the detail behind it.

## Environment
- n8n 2.41.3 (self-hosted, installed with npm and pinned), Node.js 24.19.0 (n8n 2.41.3 requires Node >= 24), Windows.
- Docker was the first choice, but its WSL2 prerequisite would not install on the development machine, so n8n runs
  natively on Node. This has no effect on the deliverables: the exported workflow imports into any n8n 2.x instance.
- `start-n8n.ps1` restricts n8n file access to the output directory, sets UTC, binds n8n to 127.0.0.1 and runs it in
  production mode (see [docs/security.md](docs/security.md)).
- The first n8n start took about 5.5 minutes with no console output while n8n created its SQLite database. The port
  opens only after migrations finish, so on a first start, check whether the database file is still growing before
  assuming a hang.

## Design decisions
| ID | Decision | Why | Alternative | Why not |
|----|----------|-----|-------------|---------|
| D-01 | n8n self-hosted | Free, visual; the exported JSON is itself a deliverable | Make / Zapier | Less transparent and harder to export and version |
| D-02 | Webhook trigger | The workflow must start automatically when a message arrives | Manual trigger with pinned data | Does not start automatically |
| D-03 | Groq `openai/gpt-oss-120b`, strict JSON-schema output | Free tier, fast, open-weight model, constrained decoding guarantees the output shape | Gemini free tier; OpenAI; Ollama | Gemini free-tier prompts may be used to improve Google products; OpenAI is not free; local Ollama is slower and hard for an evaluator to reproduce |
| D-04 | One LLM call for classification, enrichment and summary | Same input for all three; 1x latency and cost; outputs cannot contradict each other | Three calls | 3x latency, cost and failure points; cross-call inconsistency |
| D-05 | Routing and escalation are deterministic code | Business rules must be testable, auditable and not steerable by message text | LLM chooses the queue | Not testable, and prompt-injectable |
| D-06 | Persistence as append-only JSONL files | No credentials, durable, easy to inspect and version | Google Sheets | OAuth setup; adds a dependency without adding capability |
| D-07 | Confidence 0-1; escalate below 0.70 | The brief's 70% threshold | 0-100 integer | Either works; 0-1 is the common convention |
| D-08 | "Billing error > $500" = \|billed - expected\| > 500, computed in code; one known disputed amount > 500 escalates | The error is the wrong amount, not the invoice total; LLMs are unreliable at arithmetic | Use the invoice total | Would escalate sample 3 ($1,240 invoice) although the error is $260 |
| D-09 | Escalated records go only to Human Review; the team queue is kept as `intended_queue` | The brief says "instead of the standard destination" | Send to both | Duplicate work; contradicts the brief |
| D-10 | Any LLM, API or validation failure fails safe to Human Review | Nothing is silently dropped | Stop the execution | Loses customer requests |
| D-11 | API key only in n8n's encrypted credential store | Never appears in files, exports or git | `.env` file | Easy to leak into commits and exports |
| D-12 | Two outage rules: `INCIDENT` (category) and `OUTAGE_KEYWORDS` (raw text) | Sample 5 is an outage without the word "outage"; the keyword rule works even if the LLM fails | Keyword rule only | Misses sample 5 |
| D-13 | Response schema orders evidence fields before the category ("extract, then decide") | The label follows from written-down evidence and is easier to audit | Category first | The label would be chosen before the evidence |

## Assumptions
- A-01 Amounts are USD.
- A-02 Technical Question routes to customer-facing Technical Support, not an internal IT/Security team. This is arguable for the SSO question (sample 4).
- A-03 Every Incident/Outage escalates, so v1 has no separate incident queue (its intended queue is Engineering).
- A-04 Model confidence is a self-reported, uncalibrated routing signal, not a probability.

## Implementation decisions
- I-01 The workflow is generated by `scripts/build-workflow.js` from `workflow/code/*.js` and the active prompt and
  schema, so the documented prompt and the running prompt cannot drift. `--check` compares any workflow file with the
  sources without writing (ignoring IDs, positions, credentials, metadata and the machine-specific output directory).
- I-02 The output directory is a build parameter (`--output-dir` or `ARCVAULT_OUTPUT_DIR`, default `<repo>/output`).
  n8n's file nodes need resolved absolute paths, so the directory is baked in at build time; `start-n8n.ps1` uses the
  same rule for `N8N_RESTRICT_FILE_ACCESS_TO`. Portability was verified by building from a copy of the repository in
  another directory and with a different `--output-dir`.
- I-03 Queues are persistent files (`output/queue-<name>.jsonl`, Human Review in its own file) plus
  `output/triage-log.jsonl` with every record. File names come only from the code's queue table, never from input.
- I-04 The Groq call retries 3 times, 2 s apart, then takes its error output. Semantic validation failures produce a
  normal record with status `validation_failed`. Both reach Human Review through `AI_FAILURE`.
- I-05 `OUTAGE_KEYWORDS` is deliberately narrow (outage, down for all/everyone, "<service> is down", not working for
  everyone). It is a backstop, not a classifier, and does not fire on sample 5.

## Prompt revisions
| Version | Change | Result |
|---------|--------|--------|
| triage-v1 | Rubric-based prompt with category, priority and confidence definitions and extraction rules | All 5 samples matched the expected outcomes. 3 of 5 summaries had filler ("No identifiers or billing details are provided.") |
| triage-v2 | +1 summary rule: state only facts present in the message | Classification unchanged (5/5). Filler persisted in 3 summaries, plus a new one ("The account URL is provided.") |
| triage-v3 (active) | Rewrote the summary rules (what to include, an explicit ban on describing absent information or output fields, one illustrative example unrelated to the samples) and moved the same guidance into the schema's `summary` description. The validator now warns when a summary still contains filler | Run 10-3: classification unchanged (5/5), 0 filler warnings; summary set 6/6 routed as expected, 0 filler warnings |

Confidence was deliberately **not** tuned. Sample 4 (ambiguous) scored 0.95 like the others, and pushing it below
0.70 would mean fitting the prompt to the test set. It is documented as a limitation instead.

## Findings
- F-01 Confidence is coarse. Across v2 runs, 6 of the 7 AI records for the samples and edge cases scored 0.95, including the ambiguous
  sample 4. A genuinely vague message (X6) did drop to 0.55 and escalate, so the signal separates vague from clear
  text but not a clear message with an ambiguous category.
- F-02 Temperature 0 is not fully deterministic on Groq: sample 1's confidence was 0.95 in one run and 0.85 in the next.
- F-03 Groq's free tier rate-limited a burst of about 8 requests in under a minute (HTTP 429). The fail-safe handled
  it, and the test runner now has `-DelaySeconds`. Production needs a queue with backoff that honours `Retry-After`.
- F-04 The keyword backstop proved its value in a real failure: E1 escalated with no AI output at all.
- F-05 Prompt injection (X7, S7, S9) never changed a route. Even a successful injection could only change the category,
  because queues and escalation are code.
- F-06 Offline unit tests cannot catch n8n expression-engine behaviour (defect 4 below). End-to-end runs with
  inspection of the written files caught it.

## Defects found and fixed, including what AI-assisted development got wrong
The workflow was built with an AI coding assistant. These are the real cases where its output was wrong, and how they
were caught.

| # | Defect | Impact | How it was caught | Fix |
|---|--------|--------|-------------------|-----|
| 1 | The AI-drafted project notes transcribed sample 5 with a hyphen instead of the brief's em dash | Test data would not have been verbatim | Compared the notes character by character with the brief | Test data keeps the em dash; `scripts/verify.js` checks the 5 records against the samples verbatim |
| 2 | The AI's first smoke-test script built the JSON schema from PowerShell hashtables | Hashtables do not keep key order, so the schema order (D-13) was scrambled and the model answered in alphabetical order | Noticed the key order in the model's output | The schema lives in a JSON file, which keeps order |
| 3 | The AI's first prompt draft used phrases copied from the sample messages as examples | Leaks the test set into the prompt and inflates results | Re-read the draft against the samples | Replaced with generic examples; a scan confirmed no sample phrases remain |
| 4 | The AI-generated team-queue path was `...\output\{{ expression }}` | In n8n a backslash before `{{` escapes the expression, so all team records went to one literally named file, with HTTP 200 and no error | Listed the output directory after the first end-to-end run | Paths use forward slashes |
| 5 | Validator: a `null` response from the model passed as `status: ok` with no classification | Would have crashed the escalation node instead of failing safe | New validation tests, written while auditing edge cases | Non-object output fails validation |
| 6 | Validator: an identifier list returned as a string was iterated character by character | Single letters could be kept as "grounded" identifiers | Same audit | Identifier lists must be arrays of strings |
| 7 | Security review: n8n listened on all network interfaces, and error responses included stack traces with local paths | The editor and webhook were reachable from the local network; the stack traces leaked local details | `scripts/security-tests.ps1` | Localhost binding and production mode in `start-n8n.ps1`; re-tested 12/12 |

## Scope decisions
- Webhook.site delivery was replaced by queue files, because Webhook.site URLs expire and files are durable evidence.
- Not built, and discussed in the architecture write-up instead: Google Sheets view, reviewer UI, retrieval over past
  tickets, duplicate detection, labelled evaluation set, confidence calibration, Slack/Jira integration, multilingual
  support.
